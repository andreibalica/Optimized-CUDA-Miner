Introducere


Blockchain-ul este o tehnologie care a devenit cunoscută odată cu

apariția criptomonedelor, precum Bitcoin-ul, Ethereum, etc. Este o bază

de date descentralizată și distribuită a tranzacțiilor și datelor, care

funcționează pe baza unui lanț de blocuri. Fiecare bloc conține un set

de tranzacții și este legat de blocurile anterioare printr-un proces de

criptare și verificare, cunoscut sub numele de “hashing”, formând astfel

o structură sigură, imutabilă și transparentă. Dacă cineva ar încerca

să modifice un bloc, ar trebui să modifice toate blocurile următoare,

lucru extrem de dificil datorită mecanismelor criptografice.


Descentralizare: Datele sunt stocate și gestionate de o rețea descentralizată de noduri, eliminând astfel nevoia de o autoritate centrală.

Imutabilitate: Datele înregistrate în blocurile blockchain-ului sunt imutabile și nu pot fi modificate sau șterse ulterior.

Transparență: Tranzacțiile și înregistrările sunt publice și transparente, iar oricine poate să le verifice.

Securitate: Criptografia și algoritmii de consens asigură securitatea și integritatea datelor stocate în blockchain.

Algoritmul de consens


Calculatoarele participante la consens se numesc noduri (sau mineri în

cazul PoW). Aceste noduri nu se cunosc și nu au încredere unele în

altele.

Scopul unui mecanism de consens este de a aduce toate nodurile în acord,

adică de a avea încredere unul în celălalt, într-un mediu în care

nodurile nu au încredere unul în celălalt.


Minerii (aceștia veți fi voi)

efectuează lucrări de calcul în rezolvarea unei probleme matematice

complexe. Demonstrarea rezolvării problemei aduce de la sine și

încredere.

Problema matematică poate deveni mai complexă, în funcție de numărul de participanți la consens.

Structura unui bloc


Un bloc este format din:


1. Hash-ul blocului anterior, care creează conexiunea cu blocurile anterioare și asigură continuitatea și securitatea lanțului;


2. Root hash-ul tranzacțiilor (Merkle root), adică hash-ul rezultat

dintr-un arbore Merkle construit pe baza tranzacțiilor din bloc. Permite

validarea rapidă a tranzacțiilor fără a le parcurge individual.

Algoritmul este următorul:


a. Se face hash-ul fiecărei tranzacții individuale.

b. Se grupează hash-urile câte două și se calculează un nou hash pentru fiecare pereche.

c. Se repetă procesul de grupare și hashing până când rămâne un singur hash - Merkle root-ul.



Dacă există un număr impar de hash-uri într-un nivel, ultimul hash se dublează pentru a forma o pereche.


Click pentru a vedea un exemplu de calcul Merkle root


3. Nonce (Number used only once) - un număr întreg random, pozitiv, pe

32 biți, pe care minerii încearcă să îl găsească, astfel încât aplicarea

funcției de hashing, cum ar fi SHA-256, asupra block-ului rezultat prin

includerea nonce-ului la finalul blocului, să fie mai mic decât o

dificultate threshold (un alt hash, ales în funcție de numărul de 0-uri

consecutive din prefix). Munca medie necesară pentru găsirea nonce-ului

este exponențială în funcție de numărul de biți zero necesari și poate

fi verificată prin executarea unui singur hash. Nonce-ul trebuie să îl

găsiți prin metoda trial-and-error, pornind de la 0 și incrementând la

fiecare iterație, pana la valoarea maximă pe 32 biți, i.e. uint32_max.


Click pentru a vedea un exemplu de generare a hash-ului unui bloc, în urma găsirii unui nonce valid


Hash-ul blocului rezultat în urma găsirii unui nonce valid va deveni

“hash-ul blocului anterior” pentru următorul bloc de tranzacții. De aici

vine denumirea de blockchain: se creează un lanț de blocuri, iar

fiecare bloc depinde de cel anterior.



Nonce-ul valid găsit nu e unic. Pot exista mai multe nonce-uri care să

genereze un hash al blocului mai mic decât dificultatea aleasă.

Procesarea datelor

Se citesc tranzacțiile și se grupează în blocuri. La fiecare max_transactions_in_a_block

tranzacții, se face câte un bloc nou. Așadar, ultimul bloc minat

conține un număr de tranzacții egal, sau mai mic decât această valoare.

Pentru fiecare grup:

Se construiește merkle root-ul tranzacțiilor.

Se formează blocul prin concatenarea prev_block_hash și merkle_root.

Se caută un nonce astfel încât hash-ul rezultat să aibă difficulty_zeros zerouri la început.

Dacă nu se găsește un nonce valid până la max_nonce, blocul e invalidat.



În realitate, blocul include mai multe date, precum un timestamp Unix,

ceea cea oferă nondeterminism hash-ului blocului. Dacă un nonce nu e

găsit, la următoarea încercare, timestamp-ul va fi diferit, ceea ce face

din nou căutarea unui nonce o opțiune validă. Pentru o testare ușoară,

nu vom include un astfel de parametru în tema noastră. De asemenea, vom

lucra cu fișiere de input care asigură existența a cel puțin un nonce.

// Compute SHA256 and convert to hex

void apply_sha256(const BYTE *input, BYTE *output) {

size_t input_length = strlen((const char *)input);

SHA256_CTX ctx;

BYTE buf[SHA256_BLOCK_SIZE];

const char hex_chars[] = "0123456789abcdef";


sha256_init(&ctx);

sha256_update(&ctx, input, input_length);

sha256_final(&ctx, buf);


for (size_t i = 0; i < SHA256_BLOCK_SIZE; i++) {

output[i * 2] = hex_chars[(buf[i] >> 4) & 0x0F]; // High nibble

output[i * 2 + 1] = hex_chars[buf[i] & 0x0F]; // Low nibble

}

output[SHA256_BLOCK_SIZE * 2] = '\0'; // Null-terminate

}


// Compare two hashes

int compare_hashes(BYTE* hash1, BYTE* hash2) {

for (int i = 0; i < SHA256_HASH_SIZE - 1; i++) {

if (hash1[i] < hash2[i]) {

return -1; // hash1 is lower

} else if (hash1[i] > hash2[i]) {

return 1; // hash2 is lower

}

}

return 0; // hashes are equal

}


// Constructs a Merkle tree and returns the root hash

void construct_merkle_root(int transaction_size, BYTE *transactions, int max_transactions_in_a_block, int n, BYTE merkle_root[SHA256_HASH_SIZE]) {

BYTE (*hashes)[SHA256_HASH_SIZE] = (BYTE (*)[SHA256_HASH_SIZE])malloc(max_transactions_in_a_block * SHA256_HASH_SIZE);

if (!hashes) {

fprintf(stderr, "Error: Unable to allocate memory for hashes\n");

exit(EXIT_FAILURE);

}


// Compute the SHA256 hash for each transaction

for (int i = 0; i < n; i++) {

apply_sha256(transactions + i * transaction_size, hashes[i]);

}


// Build the Merkle tree

while (n > 1) {

int new_n = 0;

for (int i = 0; i < n; i += 2) {

BYTE combined[SHA256_HASH_SIZE * 2];

if (i + 1 < n) {

strcpy((char *)combined, (const char *)hashes[i]);

strcat((char *)combined, (const char *)hashes[i+1]);

} else {

// If odd number of hashes, duplicate the last one

strcpy((char *)combined, (const char *)hashes[i]);

strcat((char *)combined, (const char *)hashes[i]);

}

apply_sha256(combined, hashes[new_n++]);

}

n = new_n;

}


memcpy(merkle_root, hashes[0], SHA256_HASH_SIZE);


free(hashes);

}

Explicație: Latența lansării unui kernel de către CPU este de ordinul a 5-10 microsecunde. Pentru un număr realist de tranzacții într-un bloc (de exemplu, câteva mii), log2​(n) reprezintă un număr foarte mic de iterații (10-15 lansări). Timpul cumulat pierdut strict din acest overhead de lansare este neglijabil în raport cu timpii ceruți de temă.

Cauzele reale ale încetinirii în această abordare sunt de obicei:

    Subutilizarea masivă a GPU-ului: Pe măsură ce urci în arbore și n scade, lansezi kernel-uri care folosesc din ce în ce mai puține thread-uri (ex: 4, 2, 1), lăsând nucleele GPU-ului complet libere.

    Latența memoriei globale: La fiecare iterație (lansare de kernel), citești din memoria globală și scrii înapoi în memoria globală, un proces extrem de lent comparativ cu folosirea memoriei partajate (shared memory).

    Operațiile din interiorul kernel-ului: Dacă faci concatenări sau prelucrări caracter cu caracter la fiecare pas direct în memoria globală, penalizarea de performanță este uriașă.

Sute de mii de thread-uri care scriu simultan în rețeaua de memorie globală vor distruge performanța.

    Lipsa unui mecanism de oprire timpurie (Early Exit): Dacă un thread găsește nonce-ul valid în primele milisecunde, restul de milioane de thread-uri lansate continuă să ruleze și să calculeze SHA256 degeaba până când se termină tot grid-ul.

    Conversia costisitoare în string: Reconstrucția structurii blocului și conversia numărului întreg (nonce) în caractere/string în interiorul fiecărui thread consumă foarte multe cicluri de ceas pe GPU.

Deși funcțiile rulează secvențial (una după alta), a doua o poate influența pe prima din următoarele motive legate de managementul resurselor:

    Alocările masive de memorie (cudaMalloc / cudaMallocManaged): Dacă pentru a gestiona răspunsul de la fiecare thread ai adăugat alocări de buffere mari în interiorul buclei principale (înainte sau în timpul execuției), cudaMalloc fiind o operație sincronă și greoaie va umfla artificial timpii măsurați.

    Poluarea Cache-ului L2 și starea controllerului de memorie: Deoarece programul procesează mai multe blocuri într-o buclă, execuția anterioară extrem de grea a kernel-ului de nonce lasă memoria cache L2 a GPU-ului complet poluată și controllerul de memorie suprasolicitat. Lansarea unui număr excesiv de blocuri (de exemplu, sute de mii sau milioane, în loc de a folosi o buclă în interiorul unui număr restrâns de blocuri) penalizează sever performanța ambelor funcții, din următoarele motive:

    Latența magistralei (Bus Contention): Prea multe blocuri înseamnă un număr uriaș de cereri de citire/scriere concurente la adresele globale (cum ar fi citirea flag-ului de ieșire sau scrierea nonce-ului). Aceasta blochează controller-ul de memorie.

Da, există. Pentru a evita race condition-urile când mai multe thread-uri modifică aceeași variabilă concurent, trebuie să folosești operațiile atomice din CUDA.

O operație atomică garantează că citirea, modificarea și scrierea variabilei se execută la nivel hardware ca o singură tranzacție (indivizibilă), fără a putea fi întreruptă sau suprascrisă incorect de alte thread-uri.

Cele mai relevante funcții pe care le pune la dispoziție CUDA pentru o astfel de problemă sunt:

    atomicExch(&variabila, valoare_noua): Suprascrie valoarea de la acea adresă. Este util pentru a seta un flag global de oprire (ex: atomicExch(&nonce_gasit, 1)).

    atomicMin(&variabila, valoare): Scrie valoarea ta doar dacă este strict mai mică decât ce există deja la acea adresă. Este foarte util dacă mai multe thread-uri găsesc un nonce valid în același timp și vrei să te asiguri că îl salvezi pe cel mai mic.

    atomicCAS(&variabila, valoare_asteptata, valoare_noua): (Compare-And-Swap) Modifică variabila cu valoarea nouă doar dacă variabila este în prezent egală cu valoarea așteptată.

Un aspect critic de performanță: Operațiile atomice serializează accesul la acea adresă de memorie. Dacă pui o operație atomică într-un loc în care este apelată constant de toate thread-urile la fiecare pas, vei crea un bottleneck major și timpul de execuție va exploda. Ele trebuie apelate doar atunci când condiția a fost îndeplinită (adică, în cazul tău, le plasezi în interiorul if-ului care confirmă că hash-ul generat satisface dificultatea, nu înainte).

    Reducerea finală (ce faci cu ce a rămas de la blocuri):

        Iei ABCD de la primul bloc și EF de la al doilea bloc și le combini.

        Root-ul tău: Hash(ABCD + EF)

De ce este greșit?

Root-ul tău este Hash(ABCD + EF), dar root-ul corect Bitcoin este Hash(ABCD + EFEF).

Când Blocul 2 a redus elementele E și F, el a obținut un hash de Nivel 1. Blocul 1 a obținut un hash de Nivel 2. Reducând local, ai pierdut informația despre adâncime și ai combinat un hash de Nivel 2 cu un hash de Nivel 1.

Algoritmul oficial Bitcoin forțează hash-ul EF să aștepte, să fie urcat la Nivelul 2 prin duplicare (EFEF), și abia apoi să fie combinat cu ABCD. Reducerea ta independentă pe blocuri "scurtcircuitează" acest proces.

Este un efect de "efect de avalanșă" (sau cascadă) foarte comun în CUDA când procesezi date într-o buclă (în cazul tău: calculezi Merkle Root -> cauți Nonce -> treci la următorul bloc -> calculezi Merkle Root, etc.).

Iată explicația tehnică de ce rezolvarea celei de-a doua funcții a reparat-o "magic" și pe prima:

    Moștenirea stării proaste a GPU-ului: Când lansai milioane de blocuri la find_nonce, lăsai memoria cache L2 a GPU-ului complet poluată, iar controllerul de memorie era suprasolicitat. Când venea rândul următoarei apelări a funcției merkle_root (pentru următorul grup de tranzacții), aceasta găsea un GPU "gâfâind", plin de gunoaie în cache, și trebuia să aștepte sau să citească greoi din memoria globală.

    Coada de comenzi blocată: Lansând prea multe blocuri la nonce, coada hardware a GPU-ului (GigaThread Engine) era inundată. Lansarea kernel-urilor de Merkle (chiar dacă erau mici, logN la număr) stătea la coadă așteptând ca GPU-ul să își revină din efortul inutil anterior.

    Măsurarea timpului (Sincronizarea): Dacă măsurai timpul cu funcții de CPU (gen gettimeofday sau std::chrono) și aveai un cudaDeviceSynchronize() la începutul sau în interiorul funcției de Merkle, acel synchronize aștepta de fapt să se termine și resturile din kernel-ul precedent de Nonce, adăugând timpul penalizării de la a doua funcție direct pe factura primei funcții.

Prin reducerea numărului de blocuri la num_SMs pentru funcția a doua, GPU-ul termină munca curat, își golește perfect cozile și intră "proaspăt" și rapid în kernel-urile logN de la merkle_root! Implementarea ta pe niveluri a fost de fapt corectă și rapidă de la bun început.

Acum imi trece tot ca timp, mai putin cel mai mic test cu n foarte mic la markle, ce sa fac

Este o problemă clasică. Când volumul de date (n) este foarte mic, hardware-ul nu mai este "gâtuiala", ci overhead-ul framework-ului CUDA devine principalul consumator de timp.

Pentru testele mici, timpul de execuție este dominat de acțiunile administrative, nu de calcule. Iată cele două soluții majore, în ordinea eficienței:
1. Mută cudaMalloc și cudaFree în afara buclei principale (Cea mai probabilă cauză)

Dacă pentru fiecare grup de tranzacții (bloc) faci cudaMalloc pentru array-urile de hash-uri și apoi cudaFree la finalul grupului, acest proces omoară performanța pe testele mici. Alocarea memoriei pe GPU este o operație extrem de costisitoare (de ordinul milisecundelor).

    Soluția: Calculează la început dimensiunea maximă necesară (max_transactions_in_a_block * SHA256_HASH_SIZE), dă un singur cudaMalloc la începutul programului (înainte de a procesa primul bloc), refolosește același spațiu de memorie pentru toate blocurile și dă cudaFree abia la finalul programului.

2. Abordarea Hibridă (CPU Fallback)

Când ai un n foarte mic (de exemplu, sub 8 sau 16 tranzacții), timpul necesar pentru a trimite datele prin PCI-Express și a lansa log2​(n) kernel-uri este mult mai mare decât timpul în care CPU-ul ar face acele câteva SHA256-uri direct în cache-ul L1.

    Soluția: Pune un simplu if (n <= 16) și apelează funcția secvențială construct_merkle_root originală de pe CPU. Dacă n>16, apelezi implementarea ta pe GPU. Este o practică standard în sistemele HPC (High Performance Computing) să nu deranjezi GPU-ul pentru sarcini microscopice.
